Cine UADE

Trabajo Práctico Obligatorio de Aplicaciones Interactivas. UADE, 2.º cuatrimestre 2026. Docente: Juan Ignacio López. Integrantes: Andrei Veis, Lucas Ezequiel Manrique Simonini y Valentino Garmendia.

Resumen

  • Cliente (web): elige película, función y butacas; reserva con o sin cuenta y recibe un código. Paga en boletería o, con cuenta, online con Mercado Pago. Entra con el código.
  • Encargado (Swing): trae la cartelera de TMDB, programa funciones, cobra, vende candy, cierra la caja.
  • Acomodador (Swing): valida entradas en la puerta.
  • El sistema: no vende dos veces una butaca; calcula precios, tarifas y promociones.
  • Java 21 + Spring Boot + MySQL; React; Swing; Docker Compose. 27 casos de uso, reglas R1 a R21.

Requerimientos

  • Películas (título, duración, géneros, clasificación) y salas con su mapa de butacas.
  • Funciones sueltas o por grilla; reservar butacas concretas, cobrarlas o cancelarlas.
  • Tarifa por persona (general, menor, jubilado, estudiante) y promociones administrables.
  • Pago online por Mercado Pago Checkout Pro (sandbox; sin token, una pasarela emulada); código de acceso validado en la puerta.
  • Reservas impagas que vencen; butacas bloqueadas mientras alguien elige.
  • Candy con productos y combos; arqueo diario, borderó e informe por función.
  • Persistencia en MySQL, con la lógica independiente de ella.

Casos de uso

  • Administrador y Acomodador (solo la puerta): con contraseña, en el panel Swing.
  • Cliente: en la web, con cuenta opcional o solo con el código de su reserva.
  • Tarea de conciliación: cobra lo que Mercado Pago aprobó (detalle).

cd cine-docker
cp .env.example .env          # MYSQL_ROOT_PASSWORD, DB_PASSWORD, TMDB_TOKEN; MP_ACCESS_TOKEN opcional
docker compose up -d --build
./seed/datos-de-ejemplo.sh    # datos de ejemplo, por API
  • Web: localhost:8080; Swagger: /swagger-ui.html.
  • Panel: cd cine-swing && mvn exec:java. Usuario encargado@cine.uade.ar / cine2026; puerta@cine.uade.ar para la Puerta.
  • Instalación, token de TMDB, Adminer y problemas comunes: _other/COMO-LEVANTARLO.md.

Solo nginx publica puerto y el backend es el único puente entre las redes: ningún cliente llega a MySQL.

Llevar el servidor a otro equipo

Ninguna dirección está escrita en el código (rutas relativas, red de Docker o variable). Mudarlo: copiar repo y .env, docker compose up, abrir el panel con la dirección nueva.

Tomcat: embebido o aparte

Sin Docker, mvn package arma target/cine-api.war: corre con java -jar o en webapps/ de un Tomcat. Lo habilitan packaging war, spring-boot-starter-tomcat provided y Aplicacion extends SpringBootServletInitializer (un Tomcat externo no llama a main()).

Arquitectura en capas

  • Web (cookie de sesión) y Swing (HTTP Basic) llaman al mismo /api.
  • El backend sale a Mercado Pago y a TMDB.
  • Backend (ar.uade.cine): seis capas; cada una usa solo las de abajo. Excepción: infrastructure/, el borde — el gestor usa sus puertos y la seguridad usa un gestor en el login.
CapaResponsabilidad
controller/
  • Recibe el pedido HTTP y lo pasa al gestor.
  • Convierte el JSON en DTO y el resultado en respuesta, con su status.
  • Traduce cada rechazo a un error HTTP (ManejadorErrores).
dto/
  • La forma del JSON: Pedido*DTO entra, *VistaDTO sale.
  • Solo datos, sin lógica.
service/
  • Un gestor por subdominio: coordina cada caso de uso.
  • Aplica las reglas que necesitan la base, otras filas o la hora.
  • Abre y cierra la transacción.
model/
  • Entidades, enums y Value Objects del cine.
  • Cada entidad valida sus datos con su Validador*.
  • No sabe de HTTP ni de la base.
repository/
  • Guarda y busca entidades.
  • Interfaces: Spring Data genera la implementación.
infrastructure/
  • Lo que sale del sistema: TMDB, pasarela de pago, comprobantes, reloj.
  • La interfaz (puerto) y su implementación; Adaptadores elige cuál va.
  • La seguridad: rutas por rol y contraseñas.
  • Cada capa se divide en los mismos subdominios (candy, cartelera, ventas…): subdominio → paquete.
  • ArquitecturaTest lee los import y falla si una capa usa una que no le corresponde.
  • Spring arma todo: dependencias por constructor, nadie hace new GestorReservas(...). Si falta una, la app no levanta y dice cuál.

Convenciones

  • Enums por nombre de constante (MAS_16); fechas ISO sin zona (2026-08-13T20:30:00).
  • El precio lo calcula el backend; el monto del pago no viaja en el request.
  • Filtros por query, resueltos en el gestor: GET /api/reservas?estado=RESERVADA&q=perez.
  • Cambiar un estado es PATCH sobre el recurso ({"activa": false}), no una acción aparte. Las rutas son sustantivos: /confirmacion, /cancelacion.
  • Seguridad por rol: quién puede llamar a qué.

Hooks y estado

  • useCargar(pedir, deps) → { datos, error, previos, cargando, recargar }. datos/error son null mientras las deps no coincidan con las de la respuesta (no se ve lo de otro id); previos es lo último llegado, para que la cartelera reordene al cambiar de género.
  • Contextos SesionDelCliente y CompraEnCurso: envuelven las rutas, no se remontan al cambiar de pantalla.
  • useEffectEvent: la renovación del bloqueo lee la selección actual sin escribir un ref en el render. Lo que el render lee es estado (reservada en Confirmar), no un ref.
  • StrictMode en main.jsx: los efectos aguantan correr dos veces (el confetti marca celebrada al lanzar).

Cobrar contra cancelar

Cajero cobra y cliente cancela a la vez: las dos ven RESERVADA y ganaría la última (cancelada con pago). Con @Version en Reserva el UPDATE exige la versión leída; el segundo recibe 409 («La reserva cambió mientras se procesaba: volvé a intentarlo»). Lo prueba GestorPagosTest.

Ocupacion

Una sola definición de «ocupado en esta función» para quien vende y quien dibuja el mapa: reservas vigentes más bloqueos ajenos.

Tomar la butaca sin leer antes

Vive en la tabla bloqueo_butaca, con PK (funcion_id, asiento_id), y no en Redis: una sola fuente de verdad con las entradas y un contenedor menos. No hay SELECT previo, porque entre «está libre» y el INSERT cabe otra sesión:

  1. Un UPDATE condicional renueva la propia o toma una vencida. La base bloquea la fila y reevalúa la condición: de dos que pisan la misma vencida, gana una.
  2. Si no afectó filas, INSERT IGNORE: la PK rechaza a la segunda sin excepción, así el caso normal no deja una transacción rollback-only.

Cada sentencia corre en su propia transacción (REQUIRES_NEW): el UPDATE sin fila deja un gap lock hasta el commit, y dos sesiones con ese lock que después insertan terminan en deadlock. @Lock(PESSIMISTIC_WRITE) no sirve: FOR UPDATE no bloquea una fila que todavía no existe. OcupacionTest larga 8 hilos por la misma butaca y gana exactamente uno.

  • El monto no se recibe: se calcula al cobrar, porque el descuento depende del medio.
  • MedioPago decide R11 en los dos sentidos (el electrónico exige código, el efectivo lo rechaza), quién lleva recibo de caja y quién va por checkout.

Checkout con la pasarela

El código de autorización lo emite PasarelaPagos, un puerto con dos implementaciones (Strategy) que Adaptadores elige al arrancar, como con TMDB: con MP_ACCESS_TOKEN, MercadoPagoHttp (Checkout Pro en sandbox, java.net.http y Jackson, sin SDK); sin token, la emulada.

Mercado Pago

  • Id del checkout = external_reference (<reservaId>-<MEDIO>-<azar>): se conoce antes de crear la preferencia, así entra en la back_url sin un segundo pedido. Un id inventado da 404.
  • El retorno: GET /api/checkouts/{id}/retorno consulta /v1/payments/search; la query de la URL se ignora porque es falsificable. Recargar no cobra dos veces: si ya hay pago, no hace nada.
  • Mismo camino que la caja: registrarPago, con el mismo descuento y el mismo recibo. El medio es el que se eligió al abrir el checkout, porque de él depende la promoción.
  • Un aprobado cuenta solo si coincide monto, moneda (ARS) y un payment_type_id del medio. Si no, aviso «Mercado Pago registró un pago que no coincide con la reserva: acercate a la boletería».
  • Local: MP no muestra «Volver al sitio» ni hace auto_return con una back_url a localhost. Con una URL https (túnel) vuelve solo.

Conciliación: cobrar sin que el comprador vuelva

  • Por qué: si el comprador cierra la pestaña tras pagar, MP cobró y la reserva sigue RESERVADA. ConciliacionPagos (@Scheduled, propiedad cine.mercadopago.conciliacion, 60s) lo repara en un minuto.
  • Sin persistir checkouts: el id es el external_reference y aprobadosDesde lo recupera con una sola búsqueda de los aprobados de los últimos 30 minutos (MINUTOS_PARA_PAGAR: uno más viejo es de una reserva ya cobrada o vencida). Sin tabla ni migración. MP no filtra por prefijo, así que buscar por reserva exigiría una consulta por pendiente en cada vuelta.
  • Un solo camino: conciliarCheckout hace lo mismo que el retorno, cada id en su transacción. Es idempotente con el retorno; si MP no responde o un id falla, avisa en el log y sigue.
  • Webhook, el camino de producción: hace falta una URL https pública, notification_url en la preferencia, un POST público que valide la firma x-signature y llame a conciliarCheckout con el pago consultado a MP, no con el cuerpo. La conciliación quedaría de respaldo. No está implementado: el backend corre en localhost.

Solo el primer aprobado cobra (R5); el segundo queda en el log como «ya tiene un pago registrado» y se devuelve a mano desde MP. Evitarlo del todo exige persistir checkouts o devoluciones automáticas.
  • Queda: un aprobado que llega con la reserva ya vencida (R17) es plata cobrada sin registrar; la conciliación lo avisa en cada vuelta mientras esté en la ventana.
  • Carrera conocida: retorno y conciliación a la vez sobre la misma reserva chocan con el @Version: el segundo falla (la conciliación sigue, el retorno da 409).

Cómo se probó contra el sandbox

  • Pago sin volver al sitio: la conciliación lo cobró a los 3 segundos (1 cobrados); reserva PAGADA, CREDITO.
  • Con checkout CREDITO MP ofreció solo tarjetas de crédito.
  • Hay que entrar con el comprador de prueba del panel de MP: pagar como invitado con un vendedor de prueba da «Una de las partes con la que intentás hacer el pago es de prueba».

Precios y promociones

Entrada.precio = Funcion.precio × TipoSala × TipoAsiento × TipoTarifa
cobro          = Σ Entrada.precio − descuento de la Promocion (al cobrar)

El precio lo responde el modelo, por Experto, y cada tipo tiene su aplicarA(Dinero), sin switch. Una CalculadoraPrecio aparte tenía que conocer los tres enums y la función: una Fabricación pura que no hacía falta.

  • La tarifa es por persona y vive en Entrada; el acomodador ve qué carnet pedir.
  • El descuento vive en Pago: el 2x1 es sobre el conjunto, R15 compara montos y depende del medio de pago. R16 lo dice la tarifa: una tarifa nueva no toca el gestor.

Una jerarquía, no un switch

Factory Method y polimorfismo. El tipo se preguntaba en tres lugares: un switch en el controller, instanceof en la vista y una validación posicional en el enum. Sumar un tipo era tocar los tres, y olvidarse de uno compilaba igual. Ahora cada constante de TipoPromocion crea su subclase (NXM.crear(…) hace new PromocionNxM(…)), y cada subclase contesta calcularDescuento() y getParametros(), así la vista la describe sin preguntar su clase. Un tipo nuevo es una constante y una subclase; como los métodos son abstractos, el compilador no deja olvidarse de ninguno.

Promocion valida lo común y cada subclase lo propio, al construirse (validación): no existe una promoción inválida en memoria, y el gestor se queda solo con el nombre repetido, que necesita la base.

Control de acceso

  • Un código por reserva: el grupo entra junto.
  • No es el id: aleatorio, 8 caracteres, sin O I 0 1. CodigoDeAcceso lo genera y lo normaliza, porque se tipea a mano cuando el escáner no lee. No valida la forma a propósito: uno mal tipeado da 404 y no le cuenta a nadie cómo es uno válido.
  • Solo el día de la función (R18).
  • El ingreso es un timestamp, no un estado: el cobro es otro eje.

Candy

  • Un combo es un Producto con sus ItemCombo, no un precio suelto: permite validar R14 e imprimir el ahorro. Nace solo por Producto.armarCombo (Creador).
  • R14 del otro lado: abaratar un suelto puede dejar sin convenir a un combo que lo trae; GestorProductos revisa esos combos.
  • CompraCandy nace cobrada: lleva el medio, sin Pago ni estados, así no hace falta una FK polimórfica. R11 lo decide MedioPago, igual que en boletería.

  • El ticket sale después del commit (Observer).
  • Mantener la carta y vender cambian por motivos distintos: van separados en gestores (GestorProductos, GestorCandy) y en controllers.
  • Los productos no se borran: salen de la venta y vuelven. Nombre y precio quedan congelados en ItemCompra.

Informes por función y por período

El arqueo (GestorCaja) corta por día; borderó y recaudación (GestorInformes), por función. La fuente es el pago: una reserva impaga no vendió nada. La recaudación suma el candy atado a reservas de la función; el de mostrador no se atribuye.

El backend entrega JSON y no escribe archivos de informes: los que se suben al INCAA los genera Swing en la PC del encargado.

Declaración jurada del período

Sin fechas toma la semana cinematográfica anterior (jueves a miércoles). Entra cada función cuyo inicio cae en el período y tiene entradas cobradas: se declara lo exhibido, no la fecha del cobro. State: el estado decide qué se puede hacer

Reserva preguntaba estado == RESERVADA en cinco métodos: sumar un estado era revisarlos todos. Ahora cada constante de EstadoReserva sobrescribe solo lo que permite (RESERVADA se paga, cancela o expira; PAGADA deja ingresar), y lo demás cae en el método del enum, que rechaza. La transición devuelve el estado siguiente: estado = estado.pagar(). Nadie compara estados fuera del enum.

EstadoRevision hace lo mismo con el buzón del importador, con métodos abstractos: un estado nuevo no compila hasta decidir cada operación. Enum y no jerarquía de clases porque los estados no tienen datos, y JPA guarda el nombre de la constante sin mapeo extra.

Observer: los comprobantes, después del commit

Los gestores escribían el ticket o el recibo dentro de su transacción. Si el commit fallaba después (el @Version salta al confirmar), quedaba el recibo de un cobro que no existió; si fallaba el archivo, se deshacía una venta correcta.

Ahora el gestor publica un evento (PagoRegistrado…) y no sabe quién escucha. ComprobantesDeVentas y ComprobantesDeCandy lo reciben con @TransactionalEventListener, que Spring llama solo si la transacción confirmó, y releen por id en una transacción propia de solo lectura (REQUIRES_NEW). Si el archivo falla, la venta ya existe.

Decorator: bcrypt con un límite

bcrypt no acepta claves de más de 72 bytes. Una así solo puede venir del SHA-256 viejo, y re-hashearla en el primer login daba un 500. PasswordBcrypt implementa PasswordEncoder y envuelve al de Spring: delega todo, salvo que encode deja en SHA-256 lo que no entra en 72 bytes. Misma interfaz que lo decorado y una condición antes de delegar.

Value Objects

Un concepto con regla propia es un tipo que se valida y se normaliza al construirse, en vez de repetir la regla donde se usa el dato (la vigencia de una promoción y el rango de una grilla validaban el orden cada una a su modo). Son Dinero (centavos), Periodo, FranjaHoraria, Email (recortado y en minúsculas), Contrasena (su toString no la muestra), CodigoDeAcceso, SesionDeCompra, FormatoDeFuncion (versión, proyección y precio) y CatalogoPelicula, que se reemplaza entero para que la película nunca quede a medio validar. Periodo, FranjaHoraria, FormatoDeFuncion y CatalogoPelicula son @Embeddable: no movieron ninguna columna.

La jerarquía de rechazos

Se rechazaba con IllegalArgumentException: una librería también la tira, con un texto en inglés que llegaba al usuario, y Spring Data la traduce al salir de un repositorio, así que el 404 de exigir salía 500. Ahora es un Rechazo, con una hija por status; una IllegalArgumentException suelta es un 500 genérico y ArquitecturaTest prohíbe crearla. Sellada cierra la lista: ManejadorErroresTest falla hasta que un tipo nuevo tenga su status.

Una base para los repositorios

«Buscar por id o 404» estaba escrito 28 veces, más 8 métodos privados con su propio texto. Repositorio<T> extiende JpaRepository<T, Integer> con un método default, exigir(id, "la película"), que tira RecursoNoEncontrado («No existe la película 7»). Los 13 repositorios con id numérico lo heredan, sin clase base. @NoRepositoryBean evita que Spring Data cree un bean para la base genérica.

Dónde se valida cada cosa

  • En el DTO, solo presencia: un @Positive no lo vería el importador ni un test, y sería una segunda copia de la regla.
  • La regla es de la entidad; el código, de su validador. La entidad queda con estado y métodos con intención; lo que no puede entrar vive en model/<subdominio>/validacion/Validador<Entidad>, que llama la entidad y nunca el gestor. Se valida todo antes de asignar: una edición rechazada no deja la entidad a medio cambiar.
  • Guardas fluidas, sin cadenas de if: Regla.texto(titulo).obligatorio("Falta el título").recortado().hasta(100, "El título").valor().
  • La base cierra lo que dos pedidos simultáneos podrían colar. Los clientes no aplican reglas (ver Swing).

Preguntas de guía

Arquitectura

PreguntaRespuesta
¿Por qué dividieron el proyecto en estas capas?Para que cada cambio toque un solo lugar. ArquitecturaTest lo hace cumplir (capas).
¿Qué responsabilidad tiene cada capa?controller/ traduce HTTP, service/ aplica las reglas que piden la base o el reloj, model/ son las entidades que validan sus datos, repository/ persiste e infrastructure/ habla con afuera (tabla).
¿Qué ocurriría si colocáramos toda la lógica en el Controller?Las reglas quedarían atadas a HTTP: el importador, que da de alta por GestorRevisionCartelera, y los tests de gestor tendrían que duplicarlas.
¿Dónde debería estar una regla de negocio y por qué?En la entidad si depende de un solo objeto (Experto: R8 en Funcion); en el gestor si necesita la base (R4 en GestorReservas). Es el único paso común a API, importador y seed (dónde se valida).
¿Qué componente debería modificarse si cambiamos el motor de base de datos?application.yml, el driver, schema.sql y el único SQL nativo (INSERT IGNORE en BloqueoButacaRepository). Los gestores no: dependen de JpaRepository, y los tests ya corren en H2 (persistencia).

MVC

PreguntaRespuesta
¿Dónde está el Model en su aplicación?En model/: entidades, enums con comportamiento y Value Objects (dominio). La View son la web y Swing, que reciben *VistaDTO en JSON.
¿Cuál es la responsabilidad del Controller?Recibir el pedido, validar el DTO (@Valid), llamar al gestor y devolver el DTO con su código: POST /api/reservas → GestorReservas.reservar → 201.
¿Qué diferencia hay entre Controller y Service?El controller sabe de HTTP y no decide; el service decide reglas y transacción y no sabe de HTTP (clases).
¿Por qué la View no debería acceder directamente a la base de datos?Se saltearía reglas y seguridad y quedaría atada al esquema. Los clientes pasan por la API; en Docker ni tienen ruta a MySQL (redes).

DAO

PreguntaRespuesta
¿Qué problema resuelve DAO?Separa cómo se guarda de qué se decide: el gestor pide exigir(id, "la reserva") sin SQL (repositorios).
¿Qué responsabilidad tiene?Leer y escribir una entidad: CRUD, consultas derivadas del nombre y @Query. No valida reglas.
¿Qué ocurriría si elimináramos esta capa?Los gestores usarían EntityManager o JDBC: SQL mezclado con reglas. ArquitecturaTest lo prohíbe.
¿DAO y ORM son lo mismo?No. DAO es un patrón de acceso a datos (los *Repository); ORM, la herramienta que traduce objetos a tablas (Hibernate).

ORM

PreguntaRespuesta
¿Qué significa Object-Relational Mapping?Trabajar con objetos y que Hibernate genere el SQL: una Reserva con sus Entrada se guarda sin escribir INSERT.
¿Qué relación existe entre una Entity y una tabla?Clase = tabla, instancia = fila, atributo = columna. ddl-auto: validate y MapeoContraSchemaTest verifican que coincidan (base de datos).
¿Qué representa una relación @OneToMany?Un padre con muchos hijos: Reserva.entradas, que se guardan y borran con la reserva (anotaciones).
¿Qué ventajas tiene utilizar ORM?Sin SQL repetitivo, transacciones declarativas, base intercambiable y mapeo validado al arrancar.
¿Qué problemas puede generar una mala utilización del ORM?N+1, EAGER que arrastra grafos, lazy fuera de la transacción y escrituras perdidas. Acá el N+1 está medido por tests y @Version vuelve 409 la escritura perdida (persistencia).

PreguntaRespuesta
¿Por qué esta tabla tiene esa clave primaria?id AUTO_INCREMENT donde hay identidad; compuesta donde el par es lo único (bloqueo_butaca). Lo único de negocio va con UNIQUE (usuario.email).

HTTP/API

PreguntaRespuesta
¿Qué diferencia hay entre GET y POST?GET consulta sin efectos y sin cuerpo (GET /api/cartelera); POST crea o ejecuta una acción con cuerpo JSON (POST /api/reservas).
¿Por qué utilizaron este endpoint?Rutas por recurso y acciones como subrecurso (/api/reservas/{id}/pago); el cliente entra por código porque el id es adivinable (API).
¿Qué significa un HTTP 404?Que lo pedido no existe: «No existe la película 999», o el pago de una reserva sin cobrar (respuestas).

Diseño

PreguntaRespuesta
¿Qué patrón están utilizando?MVC en capas, Repository, DTO, Strategy, State, Observer, Factory Method, Decorator y Adapter, entre otros (dónde).
¿Por qué eligieron ese patrón?Cada uno aísla lo que cambia: Strategy el descuento, State lo que permite cada estado, Adapter el proveedor externo, DTO el contrato.
¿Qué problema solucionaría?Sin State, if (estado == …) repartidos; sin Observer, recibos de cobros que no se confirmaron; sin DTO, renombrar un atributo rompería el front (State, Observer).
¿Podrían haberlo hecho de otra manera?Sí: JDBC a mano, entidades serializadas, un switch de promociones (decisiones).
¿Qué ventaja aporta esta decisión?Cambios locales y testeables: una promo es una clase, una pasarela real otro @Bean.
