Sistema de salas de cine

Manual del TP de Aplicaciones Interactivas. Java 21 + JDBC + MySQL, aplicando el patrón DAO.

Resumen

El sistema administra la cartelera de un cine y la venta de entradas: se cargan películas y salas, se programan funciones, y los clientes reservan y pagan entradas.

Está armado en capas para que la lógica de negocio no dependa de dónde se guardan los datos. Hoy la persistencia es MySQL, pero existe una segunda implementación en memoria que se usa en los tests y demuestra que cambiar de tecnología no obliga a tocar las reglas.

Estado: el circuito de Pelicula está implementado de punta a punta. El resto del modelo está diseñado pero todavía sin persistencia. Ver Estado y pendientes.

Requerimientos

  • Cargar películas (título, duración, uno o más géneros) y salas (nombre, capacidad).
  • Programar funciones: una película en una sala, a una fecha y hora, con un precio.
  • Registrar clientes.
  • Reservar entradas para una función y luego pagarlas o cancelarlas.
  • Los datos persisten en MySQL; la lógica no depende de la tecnología de persistencia.

Modelo de dominio

Cada entidad es una interfaz con su implementación. Las asociaciones se guardan como id (peliculaId, salaId), no como referencia al objeto: el DAO resuelve la relación cuando hace falta.

Por qué los enums no llevan interfaz

Genero y EstadoReserva son catálogos cerrados. Un enum ya es un tipo con valores fijos: no hay una segunda implementación posible, así que no hay nada que abstraer.

Reserva y compra son el mismo registro

Una Reserva nace en estado RESERVADA y pasa a PAGADA cuando el cliente abona, o a CANCELADA si se da de baja. Guarda cantidad de entradas, no butacas numeradas.

El patrón DAO

DAO significa Data Access Object. Es un objeto que encapsula el acceso a los datos: la aplicación trabaja contra una interfaz y la implementación se ocupa de los detalles.

Qué problema resuelve

Si GestorCartelera conociera PreparedStatement, cambiar MySQL por archivos de texto obligaría a reescribir las reglas de negocio, que no tienen nada que ver con el almacenamiento. Con DAO, cambiar de medio es cambiar una línea en Main: 

PeliculaDAO dao = new PeliculaDAOMySQL();
// PeliculaDAO dao = new PeliculaDAOMemoria();

GestorCartelera gestor = new GestorCartelera(dao);
new MenuConsola(gestor).iniciar();

Los principios SOLID que aplica

PrincipioDónde se ve
SRP — Responsabilidad únicaEl DAO persiste, el gestor decide, el menú muestra. Nadie hace dos cosas.
DIP — Inversión de dependenciasGestorCartelera depende de PeliculaDAO, no de la implementación MySQL.
OCP — Abierto/cerradoSumar un PeliculaDAOTxt no obliga a tocar el contrato ni el gestor.
ISP — Segregación de interfacesContratos chicos: cuatro operaciones, no un DAO que hace todo.

Errores que este proyecto evita a propósito: que el DAO imprima por consola (decidiría el formato de salida y haría el dato inutilizable para otra capa), que devuelva void en vez del objeto buscado, y que SQLException se filtre hacia arriba (ataría la lógica a que la persistencia sea SQL). Por eso existe PersistenciaException.

Base de datos

MySQL 8.4 en Docker. El esquema vive en src/main/resources/schema.sql.

CREATE TABLE IF NOT EXISTS pelicula (
    id INT PRIMARY KEY AUTO_INCREMENT,
    titulo VARCHAR(100) NOT NULL,
    duracion_minutos INT NOT NULL
);

CREATE TABLE IF NOT EXISTS pelicula_genero (
    pelicula_id INT NOT NULL,
    genero VARCHAR(30) NOT NULL,
    PRIMARY KEY (pelicula_id, genero),
    FOREIGN KEY (pelicula_id) REFERENCES pelicula(id) ON DELETE CASCADE
);

La relación película–género es N:M y vive en pelicula_genero. El género se guarda con el nombre de la constante del enum, no con su posición: si mañana reordenás las constantes, la data sigue siendo correcta. La clave primaria compuesta impide repetir un género en la misma película.

El ON DELETE CASCADE hace que borrar una película se lleve sus géneros, sin código Java de por medio.

Base nueva desde cero

schema.sql está montado en /docker-entrypoint-initdb.d/: cuando alguien clona el repo y levanta el compose por primera vez, MySQL ejecuta el script solo y las tablas quedan creadas. El script corre únicamente si el volumen está vacío, así que sobre una base ya existente hay que aplicarlo a mano: 

docker exec -i apps-interactivas-mysql \
  mysql -uroot -proot -D appsinteractivas < src/main/resources/schema.sql

Para empezar de cero y perder todos los datos: docker compose down -v && docker compose up -d

Por qué Java 21 y no la última

En la máquina conviven tres JDK (17, 21 y 26). El proyecto usa 21 porque es LTS y es lo que soporta sin fricción el ecosistema (Spring, Hibernate, Lombok). La 26 es más nueva pero varias librerías todavía no la acompañan.

El pom lo deja explícito, así que el compilador valida contra la API de 21 aunque la máquina tenga otra:

<maven.compiler.release>21</maven.compiler.release>

La trampa de java_home: /usr/libexec/java_home -v 21 no filtra por versión exacta — devuelve la más nueva que cumpla. Con la 26 instalada, pedir "21" devolvía 26. Por eso JAVA_HOME apunta a la ruta del 21 de forma explícita en ~/.zshrc:

export JAVA_HOME="/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home"

Además $JAVA_HOME/bin va primero en el PATH, y el JDK 21 quedó registrado en /Library/Java/JavaVirtualMachines/ para que cualquier herramienta que enumere JVMs lo vea.

Zed

La extensión Java de Zed usa JDTLS (Eclipse JDT Language Server) para el autocompletado y los errores en vivo. Necesita un JDK 21+ para correr, y por defecto lo toma del entorno — pero Zed abierto desde el Dock no hereda el JAVA_HOME de la terminal. Por eso está fijado en settings.json: 

"lsp": {
  "jdtls": {
    "settings": {
      "java_home": "/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home"
    },
    "initialization_options": {
      "settings": { "java": { "configuration": { "runtimes": [
        { "name": "JavaSE-21", "path": "…openjdk@21…", "default": true }
      ] } } }
    }
  }
}

Abrí siempre la carpeta raíz del proyecto (donde está el pom.xml): es como JDTLS resuelve el classpath.

Qué es Maven y qué hace por vos

Tres cosas:

  1. Baja las dependencias. Declarás qué necesitás y las trae de Maven Central a ~/.m2/repository, junto con las que esas librerías necesiten a su vez (dependencias transitivas).
  2. Impone una estructura. src/main/java, src/main/resources, src/test/java y target/. Al respetarla no hay que configurar nada.
  3. Define un ciclo de vida. Fases ordenadas donde cada una corre las anteriores: compile → test → package → install. Por eso mvn package compila y testea antes de armar el jar.

Las dependencias de este proyecto

Estado y pendientes

Implementado de punta a punta: el circuito de Pelicula. Esa es la plantilla que repite cada entidad nueva.

Orden sugerido para seguir

#QuéPor qué en ese orden
1SalaDAO + gestorEs igual a Película: fija el patrón sin reglas raras
2FuncionDAO + R3Primera relación entre tablas y primera regla con lógica
3ClienteDAOSimple, pero necesario antes de reservar
4ReservaDAO + R4, R5, R6Depende de función y cliente; es la parte con más negocio

Deudas anotadas

  • PeliculaDAO no tiene actualizar: se puede crear y borrar, pero no editar.
  • El chequeo de título duplicado trae la tabla entera con listar() en vez de hacer un WHERE titulo = ?.

Cada DAO se escribe cuando se escribe el gestor que lo usa. Definir los cuatro contratos por adelantado lleva a inventar métodos que después nadie llama.

Decisiones tomadas

DecisiónAlternativa descartadaMotivo
Cupo por función Butacas numeradas Butacas exigen una tabla más y complican el modelo; el cupo alcanza salvo que la consigna pida elegir asiento

LEFT JOIN + agrupar Una consulta de géneros por película Evita el problema N+1; con INNER una película sin géneros desaparecería del listado
